# クリーニングPOS v2 作り直し 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 今の `cleaning_pos`（Laravel 8 / Vue 2）と同じ画面・同じ操作の v2 を Laravel 12 / Vue 3 で作り、XREA に並列で立て、E2E で新旧一致を確かめて 2026-10-29〜の帰省中に切り替える。

**Architecture:** `rebuild/v2` ブランチの `v2/` に新アプリを置く。画面は Blade + Vue 3 部品（今と同じ DOM/CSS）。業務ロジックは `app/Domain/*` の Service に集約し、コントローラは薄くする。旧 DB → 新 DB は `legacy:import` で何度でも入れ直せる。E2E（`e2e/`）は `E2E_BASE_URL` で新旧どちらにも流す。

**Tech Stack:** PHP 8.3、Laravel 12、MariaDB 10.6、Vue 3 + Vite 6、Bootstrap 4.6（同梱）、Pusher（private channel）、dompdf（barryvdh/laravel-dompdf 3）、league/csv、Playwright、Node 20（XREA の `~/node-v20.18.1-linux-x64`）。

**Spec:** `docs/superpowers/specs/2026-10-23-rebuild-v2-design.md`

## Global Constraints

- 画面の **配置・文言・CSS クラスは旧と同じ**。旧 Blade / Vue の DOM を写して作る（作り変えない）。`ux/refresh` の UX 変更は取り込まない。
- `feature/launch` には push しない（push で本番に自動デプロイされる）。作業は `rebuild/v2` のみ。
- 本番の XREA ファイル・本番 DB（`cleaningpossystem`）は **読むだけ**。書き込みは v2 用の場所だけ。
- PHP 8.3 / Laravel 12。`composer.json` の `php` は `^8.3`。
- サイトは **http**（プリンタが http:8008 でしか通信できない）。https へのリダイレクトはしない。
- ePOS SDK は旧の `public/js/epos-2.22.0.js` をそのまま使う。印刷命令の組み立ては旧 `ReceiptPrinter.vue` と同じ順・同じ値。
- 業務ルールの仮決め（spec §11）：
  - 税の端数：請求書＝四捨五入、納品書＝切り捨て、画面表示＝請求書と同じ。`config('pos.tax_rounding.invoice'|'delivery')` で切替できるようにする。
  - 入金確認ありの顧客の請求：作成時に `paid_at = period_end` を入れる（本番の実態 918件 vs 110件）。
  - タグ番号：数値で 1000〜10999。10999 の次は 1000。表示は `X-XXX`（10000 以上は `XX-XXX`）。
- 過去データは計算し直さない（旧の値をそのまま移す）。
- 正しい綴りで作る（`confirmation` / `ratio` / `receipt`）。画面に出る日本語は変えない。
- E2E の書き込み系は `cleaningpossystem.shop` に流さない（既存ガードを維持）。
- **spec からの変更点**：比較の基準にする旧環境は、XREA の dev ではなく **ローカルの Docker**（`infra/vps-migration` で本番ダンプ入りの再現環境と E2E 47件の成功が確認済み）にする。理由：XREA では SSH から DB を作れず（2026-10-23 確認）、dev DB は v2 の予備になりうるため。dev の修復は v2 切替後に別作業とする。

## Review Focus

1. **締め日 29/30/31 の顧客を短い月に処理** → 旧 `Utility::searchInvoicePeriod` と同じ期間になる（旧は `date('Y-m-31')` が翌月に繰り越す挙動。直さずに再現し、テストで固定）→ Task 4。
2. **同じ担当者で2台同時に注文登録** → タグ番号が重複しない → Task 4 / Task 6。
3. **会計の途中でブラウザを閉じる・通信が切れる** → 注文が中途半端に残らない（トランザクション）→ Task 6。
4. **タブを2つ開いて別の顧客を選ぶ** → 片方の注文がもう片方の顧客に付かない（顧客 ID は URL で持つ）→ Task 5。
5. **`legacy:import` を2回続けて実行** → 2回目も同じ件数・合計で、重複しない → Task 3。
