# クリーニングPOS v2 作り直し 設計書（2026-10-23）

## 1. なぜやるか

実家のクリーニング店（家族経営・1店舗）のレジシステム `cleaning_pos` を作り直す。
オーナー（開発者本人）の動機は **「中身のプログラムが今見返すといや」** で、UI への不満ではない。
UI は気を使って作ってあり、使う人（60代に差し掛かる両親と24歳の末っ子）は **今の画面の場所で操作を覚えている**。

あわせて、`.shop` ドメインの更新費が高いのでやめたい。サーバー（XREA）は安くて十分なので **XREA に残る**。VPS 移行はしない。

## 2. ゴール / やらないこと / 失敗とみなすこと

### ゴール
- G1. Laravel 12 + PHP 8.3 + Vue 3 + Vite で、**今と同じ画面・同じ操作**のシステムを新しく作る。
- G2. 今のコードの構造的な問題を作り直しで解消する（§6）。
- G3. 今のシステムと新システムに **同じ E2E を流して同じ結果** になることを合格条件にする。
- G4. XREA 内に **新旧を並べて立て**、閉店後に切り替える。旧はしばらく残して戻せるようにする。
- G5. `.shop` をやめ、XREA の無料サブドメインで運用する。外からのアクセスは今より安全にする（§7）。
- G6. **来週オーナーが帰省したとき、実機プリンタで試し印刷できる環境ができていること。**（期限）

### やらないこと（非ゴール）
- VPS 移行（`infra/vps-migration` の Docker/Caddy は本番には使わない。ローカルの E2E 環境としては流用可）。
- 画面デザインの変更・配置換え（`ux/refresh` のメニューのグルーピング等は取り込まない）。
- 複数店舗対応、新機能の追加。
- HTTPS 化（プリンタが http でしか通信できないため。§7）。

### 失敗とみなすこと（アンチゴール）
- ボタンや入力欄の **場所が変わって** 家族が迷う。
- 切り替え当日に **レシートが出ない**。
- 注文・請求・入金のデータが **欠ける・ずれる**（金額、タグ番号、請求期間、入金状態）。
- 作業中に **今の本番を壊す**（`feature/launch` は push で自動デプロイされる）。

## 4. 決まっていること（オーナーが決めた）

- 画面の **配置は変えない**。
- XREA に残る。`.shop` はやめる。URL は家族しか使わないので、IP でもサブドメインでもよい。**ただしセキュアに**。
- 店外から使うことは基本ないが、まったくないとは言えない。
- XREA 内に新旧を **並列で立てて切り替える**。
- 合否は **E2E** で判断する。
- 期限は来週。オーナーが帰省時に **実機で印刷テスト** する。そのための環境を先に用意する。

## 5. 全体構成（ビルダー判断：Claude の提案）

- **リポジトリ**：同じリポジトリの新ブランチ `rebuild/v2`。新アプリは `v2/` ディレクトリに置く（旧コードを見ながら移植できるように）。E2E はリポジトリ直下の `e2e/` を新旧共通で使う。
- **画面の作り**：今と同じく **Blade で画面を出し、Vue コンポーネントを埋め込む** 方式。SPA にはしない。
  - DOM 構造と CSS クラスをそのまま移して、見た目を同じにする。
  - CSS は今の Bootstrap 4（CDN で読んでいるもの）と同じバージョンをローカルに同梱し、二重読み込みはやめる。
  - jQuery は、使っている箇所を Vue に置き換えたうえで撤去。
- **バックエンド**：コントローラは薄く。業務ロジックは Service/Action クラス、入力は FormRequest、権限は Policy にまとめる。Web と API で重複している処理は一本化する。
- **顧客表示**：Pusher を続投（XREA 共用サーバーでは Reverb のような常駐プロセスを置けないため）。**private channel** にし、顧客表示端末用の認証を付ける。
- **プリンタ**：`ReceiptPrinter.vue` の通信手順（ePOS SDK、http:8008）は **ロジックを変えずに移す**。プリンタ IP は設定テーブルに移す。
- **ビルド**：Vite は Node 18 以上が必要。XREA のホームに Node 20 系の tarball を置いて、デプロイ時にビルドする（今の Node 16 と同じやり方）。※ XREA から nodejs.org に出られるか要確認。だめならローカルでビルドして成果物をコミットする。
- **配置先（XREA）**：
  - 新アプリ本体：`~/v2/cleaning_pos`
  - Web ルート：`~/public_html/cleaningpossystem.s239.xrea.com/`（今の本番と同じく、symlink + `.htaccess` で PHP 8.3）
  - DB：新しい DB `cleaningpossystem_v2` を作る（コンパネで作成。作成数の上限は要確認）。作れなければ dev DB を流用する。
  - デプロイ：`~/commands/pull_v2.bash`（`pull_prod.bash` と同じ形。composer install / npm build / migrate / cache clear）。cron で `rebuild/v2` を自動デプロイ。

## 6. 作り直しで直すこと（コード調査の結果。優先順）

1. **注文登録の安全化**：トランザクション、検証、タグ番号採番の排他（`lockForUpdate`）、N+1 解消（旧：`Api/OrdersController.php:37-181`）。
2. **金額計算をサーバー側に集約**：合計はサーバーで再計算する（クライアントの値は信用しない）。消費税の端数処理を1か所に（**ルールはオーナー確認 §11-Q1**）。
3. **請求書作成の一本化**：`Api/OrdersController.php:49-53` と `Api/ReturnController.php:33-37` で `paid_at` の扱いが逆（**正解はオーナー確認 §11-Q2**）。
4. **セッション持ち回りの廃止**：選択中の顧客・担当者は URL / リクエストで明示的に渡す。GET で状態を変えない（`ManagerController.php:10-18`、`CustomerController.php:61-82`）。
5. **GET でのデータ更新をやめる**：`invoice/generate` の `issued_at` 更新など。
6. **SQL インジェクション修正**：`Invoice.php:109` の `orderByRaw("FIELD(id, $ids)")`。
7. **画面からのシェル実行をやめる**：`CacheController.php:47,88` は「端末なしで Vue を再ビルドする」意図の機能（CLAUDE.md）だが、v2 ではデプロイ時に必ずビルドするので不要。画面のボタンは「キャッシュクリア」（artisan をプロセス内で呼ぶ。シェルは使わない）だけ残す。
8. **自動ログイン**：`/login/auto?id=&pass=` のように URL にパスワードを載せる方式をやめる。代わりにブックマーク用の署名付きトークン（端末ごと・失効可能）にする。
9. **API トークン**：画面表示ごとの Sanctum トークン発行をやめ、同一オリジンのセッション認証（Sanctum SPA 方式）にする。
10. **権限チェック**：Policy で「自分の店舗のデータか」を確認する（今は1店舗だが、ID 直指定で何でも触れる状態をなくす）。
11. **マジックナンバー**：`store_id 1`、`Ipaddress::find(1)`、カテゴリ id≠1、プリンタ IP を設定に移す。
12. **綴りの修正**：`confimation` / `raito` / `Recipt` など。新スキーマでは正しい綴りにして、移行スクリプトで変換する。**画面に表示される文言は変えない**。
13. **タグ番号の折り返し値**：`addTag` は 10999→1000、`Order.php:382` は 9999→1000、CLAUDE.md は「9-999 → 0-001」と、3通りに食い違っている（**正解はオーナー確認 §11-Q3**）。
14. 不要パッケージの撤去：livewire（未使用）、adminlte（未使用なら）、laravel-cors、swiftmailer、goodby/csv（→ league/csv）、moment（→ dayjs）。

認証モデルは今の「店舗アカウントでログインし、画面で担当者を選ぶ」運用を変えない（`stores` = ログインアカウント、`managers` = 担当者）。

## 7. セキュリティとアクセス（ビルダー判断）

プリンタが http でしか通信できない。https のページから http のプリンタへの通信はブラウザに止められるので、**サイトは http のまま** にする。代わりに入口を絞る。

- **店内**：お店の固定回線の IP からは、今まで通りログイン画面だけで入れる。
- **店外**：ログイン画面の手前で **Basic 認証（もう一つの合言葉）** を求める。
  - Apache 2.4 の `<RequireAny> Require ip <店のIP> / Require valid-user </RequireAny>` を `.htaccess` で設定する（XREA で使えるかは要確認）。
  - **店の IP が固定かどうかは要確認**。変わる回線なら、全員 Basic 認証にする。
- ログインの試行回数制限（throttle）。
- `APP_DEBUG=false`、`APP_ENV=production`。
- 顧客表示は private channel にする。表示端末は専用トークンでログインする。
- ※ http なので、通信経路の盗聴は防げない。プリンタの https（port 8043）で印刷できると確認できたら、https 化を別案件にする。

## 8. データ移行

- `v2/database/migrations` は新スキーマ（綴り修正・設定テーブル追加）。
- 移行コマンド `php artisan legacy:import`：旧 DB（読み取り専用の接続）→ 新 DB へ全テーブルを変換して投入する。**何度でもやり直せる**（毎回、新 DB を空にして入れ直す）。
- 移行後の検算：件数、金額合計（注文・請求）、未払い件数、最新タグ番号を、旧と新で突き合わせて出力する。1つでも違えば失敗にする。
- `sessions`、`personal_access_tokens`、`client_errors` は移さない。
- **過去データは計算し直さない（ビルダー判断）**：金額・`paid_at`・タグ番号は旧の値をそのまま移す。Q1〜Q3 で決めたルールは、切替後に作られるデータにだけ適用する。だから検算は「旧と完全一致」で判定できる。
- 移行前に `stores` の行数と使われ方を確認する（`Auth::id()` を `store_id` として使っているため）。複数アカウントが同じ店のデータを共有していたら、Policy の設計を見直す。

## 9. E2E（合格基準）

- **「同じ結果」の定義（ビルダー判断）**：家族が画面で見るもの・帳票に出るもの（表示される金額、タグ番号、請求期間、入金状態、画面の配置と文言）が同じであること。URL・HTTP メソッド・内部の持ち方（セッション廃止、GET→POST、自動ログイン方式）は比べない。§6 で **わざと挙動を変える点**（Q1〜Q3 の結果）は `e2e/allowed-diffs.md` に一覧化し、旧と新で期待値を分ける。一覧にないずれは不合格。
- **テストを流す場所（ビルダー判断）**：切替前の v2 は本番 DB の **コピー** なので、XREA 上の v2 にも書き込み系の E2E を流してよい。テスト用の店舗・担当者は Docker スクリプトではなく `php artisan e2e:seed`（v2 に作る）で用意する。切替時に、本番拒否ガードの対象へ v2 の URL を加える。
- 既存の `ux/refresh` の E2E（52件）を `e2e/` に取り込み、**新旧両方の URL に同じテストを流す**（`E2E_BASE_URL` で切替）。
  - UX 刷新の分（`ux.spec.js` など、配置変更を前提にしたもの）は除く。
- 書き込みを伴うテストは本番に流さない（既存 config の本番拒否ガードを、新 URL 名でも維持する）。
- **比較の基準にする旧環境**：dev（`dev.cleaningpossystem.shop`）を `feature/launch` の最新まで追いつかせ、本番 DB のコピーを入れる。dev の自動更新が止まっている原因もここで直す。
- 追加するテスト：
  - 請求期間の計算（締め日ごと）、税の端数、タグ番号の採番と折り返し、入金状態、PDF（請求・日報）が開けること。
  - 画面の **配置の同一性**：主要画面のスクリーンショットを旧と新で比べる（Playwright の `toHaveScreenshot`、多少の差は許容）。
- プリンタと Pusher は E2E では接続しない（既存どおり無視リスト）。印刷データの組み立て（ePOS に渡す命令列）は、プリンタの代わりのスタブで旧と新を比較する。

## 11. 業務ルール Q1〜Q3（オーナー回答：**仮でよい**。帰省時に実際の紙と見比べて確定）

仮の正解は「今お客さんに実際に出ている結果と同じになる方」（ビルダー判断）。

- Q1. 消費税の端数（今は画面＝切り捨て、請求書＝四捨五入、納品書＝切り捨てで混在）
  - **仮：お客さんに渡る帳票と同じにする**。請求書は四捨五入、納品書は切り捨て。画面の表示は請求書に合わせる。
  - 金額計算クラスでは、端数処理の方法を設定値として持ち、確定したら1か所を変えるだけで済むようにする。
- Q2. 入金確認が必要なお客さんの `paid_at`（注文時に入れる `OrdersController` / 入れない `ReturnController`）
  - **仮：本番データで多数派の方に合わせる**。移行前に、本番 DB で該当する請求の `paid_at` の実態を集計して決める。
  - 集計で決めきれない場合は、コメント「埋めない」に合っている `ReturnController` 側にする。
- Q3. タグ番号の戻り先（9-999 → 0-001 / 9-999 → 1-000 / 10-999 → 1-000）
  - **仮：実際に番号を振っている `addTag` の動き（10-999 → 1-000）に合わせる**。本番の `tag_numbers` の現在値も確認する。連続判定（`Order.php:382`）もこの範囲にそろえる。
- 3つとも `e2e/allowed-diffs.md` に「仮」と書き、確定したら更新する。
