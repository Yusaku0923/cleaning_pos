# 旧 → v2 で許容する差分

旧(Laravel 8 / Vue 2)と v2(Laravel 12 / Vue 3)の E2E・画面比較で、**差が出ても不合格にしない項目**。
「仮」は現時点の想定で、v2 実装・業務確認のうえで確定または撤回する。それ以外の差は不具合として扱う。

## 許容する差分(仮)

すべて **仮**。業主が 10/29 に実際の紙の帳票と突き合わせて確定する(確定までは下表を期待値として扱う)。
根拠は `.superpowers/sdd/2026-10-23-rebuild-v2/global-constraints.md` の「業務ルールの仮決め」。

| 項目 | 旧の値 | v2 の値(仮) | 意図した差分 |
|---|---|---|---|
| 税の端数 | 画面表示 = 切り捨て(`trunc`)、請求書 PDF = 四捨五入、納品書 = 切り捨て | 請求書 = 四捨五入、納品書 = 切り捨て、**画面表示 = 請求書と同じ(四捨五入)**。`config('pos.tax_rounding.invoice'\|'delivery')` で切替 | **画面表示だけ**旧と違う(旧: 切り捨て → v2: 四捨五入)。請求書・納品書は旧と同じ。例: 内税10%・税込 500 円 → 画面の内消費税は旧 45 円(切り捨て)、四捨五入でも 45 円で同じ。端数が .5 以上になる金額(例: 税込 505 円 → 旧 45 円 / v2 46 円)で差が出る |
| `paid_at`(入金日時) | 注文経由: 入金確認ありの顧客は請求作成時に `paid_at = period_end`、それ以外は `null`。**返却経由は逆**(`ReturnController`: 入金確認ありは `null`、それ以外は `period_end`) | 注文・返却の両方で、入金確認ありの顧客は `paid_at = period_end`、それ以外は `null`(`InvoiceService::findOrCreateFor`) | **返却経由の請求**だけ旧と逆になる(入金確認あり: 旧 `null` → v2 `period_end`、なし: 旧 `period_end` → v2 `null`)。注文経由は同じ。繰越・締日整列で作る請求書は旧と同じく `null`。過去データは計算し直さず旧の値のまま移す |
| 請求期間の存在しない日 | `Utility::searchInvoicePeriod` は `date('Y-m-<締め日>')` の文字列を返す。締め日 0(顧客登録の「日付を選択してください」の値。本番 335 人)だと終了日が翌月の `YYYY-MM-0` になり、DB に **`YYYY-MM-00`** が入る(本番 請求書 1281 / 1289 の `2026-07-00` / `2026-08-00`、注文 1550 の `paid_at` `2023-11-00`)。締め日 29〜31 の短い月は `2026-02-31` / `2026-01-32` のような文字列になり、DB には **`0000-00-00`** が入る(PHP で読むと `2026-03-03` のように繰り上がるか、32 日は読めない) | 旧が存在する日を返す場合は旧と完全に同じ日。存在しない日の場合は本当の日付にする: **終了日 = その月の min(締め日, 月の日数)**(締め日 0 と 99 は月末)、**開始日 = 前の期間の終了日の翌日**。渡し日は必ずその期間に入る(例: 締め日 30・3/1 渡し → 旧 `2026-02-31`〜`2026-03-30`、v2 `2026-03-01`〜`2026-03-30`) | 締め日 0 の顧客(旧 `YYYY-MM-00` → v2 その前月の末日)と、締め日 29〜31 の短い月(画面では選べず本番にもない)だけ。締め日 1〜28・99 は旧関数の実行結果(`v2/tests/fixtures/invoice_periods.json`)と全件一致。取り込んだ旧の `-00` の行は値を変えずに移し、v2 は同じ期間の請求書として使う(終了日が月末の期間なら `翌月-00` の請求書も一致とみなす)。締日ズレの判定も締め日 29〜31 は min(締め日, 月の日数) で比べる(締め日 0 は旧と同じく常にズレ) |
| タグ番号 | 数値 1000〜10999。採番の `addTag` は 10999 の次が 1000。表示 `X-XXX`(10000 以上は `XX-XXX`)。ただし連番判定(`Order::isConsecutiveTag`、Order.php:382)は 9999 → 1000 だけを「連続」とみなす | 採番・表示は同じ。連番判定は **10999 → 1000 を連続**とみなす | 折り返し境界(10999 → 1000)での**まとめ表示・連番判定だけ**旧と違う(旧: 9999 → 1000 が連続、v2: 10999 → 1000 が連続)。採番値と表示は同じ |
| 割引 (%) の値引額 | 画面 (`DiscountModalComponent`) が浮動小数で `Math.floor(合計 * (割合 / 100))`。その値をそのまま保存・印刷 | 画面もサーバー (`PriceCalculator::reduction`) と同じ整数計算 `floor(合計 × 割合 / 100)`。保存・印刷・画面の合計はサーバーの値で一致 | 浮動小数の誤差が出る組み合わせ(単価 10〜30000 円 × 1〜100% の 300,000 通り中 1,634 通り)だけ値引が 1 円多く、合計が 1 円少ない。例: 1,500 円 × 29% → 旧 値引 434 / 合計 1,066、v2 値引 435 / 合計 1,065。100 円 × 29% → 旧 28、v2 29 |

## 許容する差分(確定: セキュリティ)

| 項目 | 旧 | v2 | 意図した差分 |
|---|---|---|---|
| 顧客表示 (`/customer_display`) | 未ログインで誰でも開ける。Pusher の**公開**チャンネル `cleaning-pos` に顧客名が流れ、鍵を知る誰でも購読できる | 表示端末は `GET /display/login/{token}`(`php artisan display:issue-token` で発行)でログインし、店舗ごとの **private** チャンネル `private-store.{店舗ID}.display` だけ購読できる。未ログイン (またはログイン切れ) は `/login` へは飛ばさず、スタッフ向けの案内「顧客表示の再ログインが必要です（スタッフ向け）」を全画面で出す (401)。ログインは remember cookie (365 日) と 10 分ごとのキープアライブで保持。表示端末のログインでは POS の画面・API は使えない | 開き方(ログイン)とチャンネル名だけ。画面の DOM・CSS、イベント名 `customer-display`、ペイロード `{message: {event, ...}}`、送るきっかけ(顧客選択・顧客登録・預り入力を開く・会計後の「終了」)は旧と同じ。顧客選択は GET の代わりにリダイレクト先の画面が POST で送る |
| 端末の自動ログイン | `GET /login/auto?id=<メール>&pass=<パスワード>` で、URL のパスワードでログイン (`Referrer-Policy: no-referrer`、連続した誤りは 429) | `/login/auto` は無い (404)。端末ごとのトークンの `GET /login/device/{token}` (`php artisan device:issue {名前} --store=`、`device:revoke`)。誤り・取り消し済みは 404、`throttle:10,1` で 429、成功時は `Referrer-Policy: no-referrer` (表示端末の `/display/login/{token}` も同じ) | 端末のブックマーク URL (切替時に作り直す)。smoke の `/login/auto` 3 件は v2 では `/login/device` で同じ観点を確かめる。正しいトークンでのログインは `E2E_DEVICE_URL` (発行した URL) があるときだけ流す |
| API の認証 | 画面表示のたびに Sanctum の個人トークンを `:token` で画面に埋め込み、API は `Authorization: Bearer` | API トークンを作らない。Sanctum の SPA セッション cookie + `X-XSRF-TOKEN` | 画面に `:token` が無い。smoke「APIトークンは…再利用される」は v2 では「画面にトークンが無く、セッションだけで API が通る」を確かめる |

## 許容する差分(確定: 旧の不具合の修正。お渡し・入金・履歴・タグ変更)

| 項目 | 旧 | v2 | 意図した差分 |
|---|---|---|---|
| 請求書に載った注文の取り消し | 注文は消えるが、空になった請求書の削除で 500 (`Invoice::orders()` 未定義)。請求書は残る | 1 トランザクションで注文・品物を論理削除し、請求書に他の注文が残っていなければ請求書も論理削除して 200。ただし発行済み (`issued_at` あり)・繰越の元/先の請求書は空でも残す | 500 にならない。空の未発行請求書が残らない |
| 取り消し時の顧客集計 | 預り一覧からは画面が送った顧客で累計売上・来店回数を戻す。全体検索 (`customer_id: null`)・ホームの直前預り取り消しでは戻さない。品物 (`order_clothes`) は残る | どの経路でも注文の顧客で戻し、品物も論理削除する | 全体検索・直前預り取り消しのあとの累計売上・来店回数 |
| 伝票詳細のタグ編集 | 先頭 1 文字で分けるので `10-XXX` は `1` / `0-X` と読まれる。保存値の確認なし | `-` で分ける。保存は 1-000〜10-999 だけ (それ以外は 422 で保存しない) | `10-XXX` のタグ・範囲外の値 |
| タグ番号更新 (ホーム) | 空欄・範囲外もそのまま `tag_head * 1000 + tag_body` を保存 (空欄なら 0) | 入力欄と同じ範囲 (1〜10 / 0〜999) のときだけ保存。保存値は旧と同じ式 | 空欄・範囲外のときは変えない |
| お渡し・入金・取り消し・タグ編集の対象 | ID さえ送れば他店舗の注文・品物も変えられた | 自店舗のものだけ (他店舗は 404)。お渡しは 1 伝票の品物だけ (複数伝票なら 422) | 画面からの操作では差は出ない |

## 許容する差分(確定: 旧の不具合の修正。請求・入金確認・日報)

| 項目 | 旧 | v2 | 意図した差分 |
|---|---|---|---|
| 請求書の「印刷」と発行済みの記録 | `GET /invoice/generate?ids=` が PDF を返すついでに `issued_at` を入れる。`ids` を SQL にそのまま埋め込む (`FIELD(id, $ids)`) | 画面が先に `POST /invoice/issue {ids}` で `issued_at` を入れ、続けて `GET /invoice/pdf?ids=` を新しいタブで開く (GET は表示だけ)。`ids` は正の整数のカンマ区切りだけ (それ以外は 422)、`FIELD(id, ?, ...)` はバインド。他店舗・削除済みの請求書が混ざれば 404 | 画面の操作・PDF の中身・発行後の青枠は同じ。何も選ばずに「印刷」: 旧は新しいタブが 500、v2 は何もしない |
| 入金確認の「入金確認」 | 請求書 ID を注文 ID として `/api/payment` に送る。**同じ ID の別の注文**が入金済み (`payment` = 入力額) になり、請求書は未確認のまま一覧に残る | `POST /api/invoice/payment_confirmation {invoice_id, payment}` で**その請求書**の `paid_at` に今日を入れ、一覧から消える。入力額は受け取るが保存しない (請求書に入金額の列がない) | 確認した請求が一覧から消える。別の注文は書き換わらない |
| 入金確認で請求を選び直す | 前に選んだ請求の伝票が右の一覧に残り、下に足されていく | 選んだ請求の伝票だけを出す | 2 件目以降を選んだときの右の一覧 |
| 繰越・締日整列・検索の対象 | ID さえ送れば他店舗の請求書・担当者も扱えた。締日整列は配列の 1 件目以外も処理するが、削除する請求書自身に注文を戻す旧の不具合あり (Task 4) | 自店舗のものだけ (他店舗は 404、何も変えない)。選んだ請求書を 1 件ずつ `InvoiceService::carryOver` / `alignCutoff` で処理 | 画面からの操作では差は出ない |
| 日報の日付 | `?date=` / `generate/{date}` に日付でない値を入れると 1970 年の日報 | 実在する `Y-m-d` 以外は 404。PDF の URL は `daily-report/{date}/pdf` | 不正な日付のときだけ |
| 請求書 PDF の消費税 | Blade で `amount - round(amount / (1 + 税率))` | 同じ式を `PriceCalculator::includedTax(..., config('pos.tax_rounding.invoice'))` で計算 (既定 `round` で旧と同じ値。本番ダンプの請求 3 件で旧と一致: `v2/tests/fixtures/legacy_invoice_totals.json`) | 設定を `floor` にしたときだけ |

## 許容する差分(確定: 納品書)

| 項目 | 旧 | v2 | 意図した差分 |
|---|---|---|---|
| 納品書の取引先の範囲 | `delivery_customers` に店舗の列が無く、どの店舗でログインしても全取引先が出る | 取引先は店舗ごと (`store_id`、取り込みでは最初の店舗 (本番の店舗 ID 1) に付ける)。自店舗の取引先だけ出る | 本番の店舗の画面は同じ。E2E 店舗では旧は本番の取引先 2 件、v2 は `E2E納品先` 1 件。画面比較「12 納品書」は 1 件目のカードだけ残して比べる |

## スモークの扱い (Task 12)

- `/login/auto` 3 件・API トークン 1 件: 上の「端末の自動ログイン」「API の認証」のとおり v2 は別の仕組みで同じ観点を確かめる (skip しない。トークンでのログイン成功だけ `E2E_DEVICE_URL` が要る)。
- スマホ UA の `/` → `/delivery/sp/choice` (delivery.spec): 旧と同じ動き (v2 の `HomeController` が同じ正規表現で判定)。v2 でもそのまま流して PASS。ログイン後の行き先も旧と同じ (`LoginController::redirectPath`)。

## 比較対象外

- **URL の変更**: v2 でパスが変わるのは許容する(例: 担当者・顧客選択が `/manager/update/{id}` や `/customer/select/{id}` ではなく URL 方式になる)。E2E は `tests/helpers.js` の `E2E_TARGET` 分岐で吸収し、画面操作(クリックする要素)は同じにする。
- **HTTP メソッドの変更(GET → POST など)**: 状態を変える操作を GET から POST に直すのは許容する。画面上の操作結果だけを比べる。
- API の内部 URL・レスポンスの形(画面から見えない部分)。
- `APP_ENV=local` のときだけ出る開発用ボタン(メニューの「キャッシュクリア」など)。表示条件は旧と同じ `config('app.env') === 'local'` だが、旧の Docker は local ではなく v2 の Docker は local なので、ローカルの画面比較「03 メニュー」はこの行の分だけ差が出る。v2 は「Vue再ビルド」「キャッシュクリア + Vue再ビルド」(サーバーで npm を実行)を作らない(Task 10)。本番(`production`)では出ないので画面は同じ。
- 実行ごとに変わる値: 現在時刻、日付入力、発行予定タグ番号、伝票No.、請求の対象月・対象期間、来店日・来店回数・金額(画面比較では mask で隠す)。
- 取引先名・カテゴリなど本番マスタ由来の文字列(個人情報を含みうるため mask で隠す)。

## 運用

- E2E は毎回同じ状態から始める。`bash e2e/setup-test-store.sh` が E2E 顧客の注文・請求を消し、集計・タグ採番を初期値に戻す(E2E 顧客以外は触らない)。order-flow は作った注文をすべて削除し、削除の成功を検証する。

- 許容差分を増やすときは、この表に「旧の期待値・v2 の期待値・理由」を書いてから行う。
- 基準画像は旧の Docker 環境で作る(`docker-compose.legacy.yml`、手順は本ファイル末尾)。

## 旧の基準環境

```bash
# 初回のみ: 本番ダンプを tmp/legacy.sql.gz に置く(git 管理外。個人情報を含むのでコミット禁止)
docker compose -f docker-compose.legacy.yml up -d --build     # http://localhost:8081 (DB は 33061)
bash e2e/setup-test-store.sh                                   # E2E 用データ(test@gmail.com / Test123456)
cd e2e && E2E_BASE_URL=http://localhost:8081 E2E_TARGET=legacy npx playwright test
# 基準画像の作り直し
E2E_BASE_URL=http://localhost:8081 E2E_TARGET=legacy npx playwright test tests/parity --update-snapshots --project=parity --no-deps
docker compose -f docker-compose.legacy.yml down               # 停止(DB も消すなら -v)
```
